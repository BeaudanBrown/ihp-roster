# Replace roster profiling spine with OpenTelemetry

Move the request/render profiling spine from custom Server-Timing and X-Profile-Counters headers to OpenTelemetry traces and low-cardinality metrics while preserving roster-specific HTML/render diagnostics and giving coding agents first-class access to profile results.

## Design

Adopt the `hs-opentelemetry-*` package family with OTLP export as the application tracing spine. The current nixpkgs `hs-opentelemetry-instrumentation-wai` package is marked broken only because its published Cabal upper bound still says `hs-opentelemetry-api ==0.2.*`; a project Nix `doJailbreak` override has been verified to build against the available `hs-opentelemetry-api-0.3.0.0`, so use that instead of switching to the separate `opentelemetry-wai` stack.

Keep `IHP_ROSTER_OTEL` separate from `IHP_ROSTER_PROFILING`: OTel request tracing should be safe for staged/prod sampled use, while heavier HTML pre-render/component byte profiling remains diagnostic-only. Treat normal production OTel as a lightweight mode: WAI request/root spans plus cheap child spans and attributes only. Byte-counting, forced HTML rendering, render counters, and compatibility headers stay behind the existing diagnostic profiling gate unless a future ticket explicitly adds another opt-in gate.

Bridge existing `profileActionSpan`/`profileActionSpanWithDetail` semantics into OTel child spans instead of deleting the semantic instrumentation. Bridge `profileHtmlComponent`/`profileCounter` details to OTel only in diagnostic/profile runs where the current byte/counter cost is intentional. Avoid PII: no names, emails, raw query strings, or high-cardinality staff/slot/user/venue ids by default.

Route naming should use IHP action constructor names where possible. WAI middleware cannot infer the action constructor by itself; add a lightweight controller/action annotation helper that can be called from controller `beforeAction` and uses the already-derived `Data` instances to set/update `http.route`/span name to low-cardinality values such as `ShowRosterWeekAction` without ids.

Provide agent access first through local profile artifacts and a project Pi extension. The first local backend should be a Nix-managed OpenTelemetry Collector path that can export traces to bounded local files under the profile run directory and produce compact JSON/Markdown summaries. Grafana Tempo/Grafana/Prometheus-compatible metrics and Grafana MCP remain the richer backend integration once needed, but should not block the initial agent/debugging workflow.

Expose observability/profiling runtime controls through the project NixOS module options rather than ad-hoc environment setup. Module options should cover enabling OTel, service name, OTLP endpoint, sampler/sampler arg, optional local collector/profile services, and the existing diagnostic profiling gate.

## Acceptance Criteria

Requests produce useful OTel root and child traces; roster render spans expose component duration/bytes and request-shape counters; stable low-cardinality metrics are available for response/component bytes and render durations; local/profile runs produce agent-readable OTel summaries; coding agents can run a low-rate profile and query/compare results through tools; custom X-Profile-Counters are deprecated or compatibility-only; existing profiling remains default-off and production-safe.
