# Audit InteractionContract boundary and stop for follow-up approval

Audit InteractionContract for generic versus surface-specific vocabulary and stop for user approval before any broad reshaping.

## Design

Classify InteractionContract values as generic interaction runtime vocabulary, Roster-specific values that should move under RosterSurface, or duplicated HTMX method/swap definitions that can safely reuse the shared model. Do not perform broad interaction architecture changes in this ticket. If non-trivial migration is recommended, produce a proposed follow-up ticket split and ask the user before creating or implementing it.

## Notes

**2026-07-08T06:09:35Z**

InteractionContract audit findings (planning gate):\n\nGeneric runtime vocabulary to keep in InteractionContract for now: activation triggers; field presence; conflict resolution; effect sources; session/effect/selector/target/intent-form/capability record shapes; DOM attrs for interaction mount/layer/intent fields; pointer field names used by the generic runtime. These describe the interaction engine rather than one feature page.\n\nRoster-specific vocabulary currently mixed into the global contract: InteractionSurfaceFamily has only Roster; InteractionIntentName has set-roster-layout-mode and move-roster-shift-to-slot; InteractionIntentFieldName includes rosterLayoutMode plus drag/drop fields currently only emitted by RosterSurface; InteractionStaticSchemaRegistry has a hard-coded roster key; generated InteractionStaticSchemas currently contains only roster schema data. These should eventually be derived from registered FrontendSurface interaction declarations rather than declared as global enum cases.\n\nDuplicated HTMX vocabulary: InteractionContract declares HtmxMethod and HtmxSwap separately from the shared generated HTMX metadata model introduced in ir-e0g8. IntentFormContract should eventually reference/reuse that shared method/swap vocabulary or a common generated schema instead of maintaining duplicate enums.\n\nRecommendation: do not reshape in this ticket. Proposed follow-up split, pending user approval: (1) derive InteractionSurfaceFamily/StaticSchemaRegistry from registered surfaces; (2) move surface-specific interaction intent names/field names/layer names to surface-scoped generated aliases while preserving TS compatibility shims; (3) deduplicate IntentForm HTMX method/swap schemas against the shared HTMX metadata model; (4) add compatibility/guard tests before deleting old global names. Stopping here for approval before creating or implementing these follow-up tickets.
