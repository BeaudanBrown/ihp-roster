# Collect DB runtime and richer cache profiling metrics

Broaden profiling output beyond manual spans so reports can explain whether latency comes from SQL, render work, runtime pressure, cache behavior, or live-update fanout.

## Design

Add request-level counters for DB query count/time, slow query grouping where practical, response render/serialization time, response bytes, projection cache hit ratio/size, live-update subscriber/fanout counts, and lightweight runtime/GC/process metrics in profiling reports. Keep high-cardinality values out of Server-Timing; prefer structured artifacts/log lines for detailed data.

## Acceptance Criteria

profile-app/profile-load artifacts include DB/query, render, cache, live-update fanout, and runtime summary fields where available; Server-Timing remains compact and standards-friendly; metrics have clear names and units; reports rank likely bottleneck class per route.
